# AI Jarvis and the Empowered Human Workforce

## Chapter 6 companion: Delegate a result that another person can accept

Original teaching draft, October 20, 2026. Prepared with AI assistance at the project owner's direction for The Evolutionary Evolutions Creative Creations Studios of Intergalactic Corporate Services LLC. This is a new repository teaching example associated with the planned Book One subject of delegation and acceptance criteria. It is not the complete book or a replacement for an earlier manuscript edition.

### What the reader will be able to do

By the end of this lesson, you should be able to give an assistant a bounded production assignment, explain what evidence would make its result acceptable, and identify which adaptations need attention after a source changes. You will practice with public teaching material. Your final submission is a small project packet and an explanation of a deliberately introduced failure.

The people, organization, conversations, decisions, and workplace events below are invented for teaching. They are not customer results, employee records, or evidence of a business benefit. The production commands accompanying this lesson can be checked separately; the fictional team does not certify them.

### 1. Start with the person who needs the result

Nadia runs a small training studio. Leo helps prepare lessons. Inez reviews technical explanations. Their next assignment sounds simple: turn a short lesson about coordinating AI work into a readable chapter, an audio script, a short video script, and a chapter-based video storyboard.

On Monday, Nadia says, "Make something impressive about AI assistants." Leo returns with twenty possible titles, several striking slogans, and a long list of proposed tools. Nadia still cannot decide what to teach. Inez cannot tell which claims need checking. The work contains ideas, but the assignment has not reached the point where another person can accept a result.

Nadia rewrites the request. "Help a first-time studio operator prepare one reviewable assignment. The reader should be able to name the required output, identify its source version, and explain what must happen when that source changes. Use a fictional production team and local text files. Finish with an exercise the reader can perform without a paid AI account."

This request tells Leo whose work should improve and what the person should demonstrate. It also limits the production burden. The pilot can test the explanation before anyone records an audiobook, designs a full book, or buys advertising.

The first useful unit of delegation is a result someone can inspect. A broad ambition supplies direction. The bounded assignment connects that ambition to an artifact, a reviewer, and a next decision. A studio can still pursue a large book series while asking each production cycle to deliver a small, coherent part of it.

### 2. Separate the requested artifact from the desired outcome

The artifact in this pilot is a chapter with three adaptations. The desired outcome is a reader's ability to direct work and recognize stale evidence. These require different checks.

A file check can establish that four text files exist. A hash check can establish that a file matches recorded bytes. An editorial review can examine whether the explanation is clear. A learner exercise can show whether one reader can apply the idea. None of those observations alone proves the entire desired outcome.

This distinction changes how the team uses assistants. A drafting assistant can prepare a candidate explanation. A structural checker can identify missing sections. A separate reviewer can challenge the logic. The learner must still demonstrate understanding through an assignment that does not simply ask them to repeat the chapter's wording.

Nadia writes three acceptance questions before delegating:

1. Can the reader produce a brief containing an objective, audience, source list, and concrete definition of done?
2. Can the reader explain why a changed manuscript may require a new narration or storyboard review?
3. Can the reader distinguish a verified text packet from a recorded, reviewed, and released media product?

The team can now discuss quality in terms of observable work. "Make it more professional" becomes "Show the reader how to detect a changed source, and explain what the check cannot prove." That is a useful instruction for both people and assistants.

### 3. Write the assignment before multiplying the agents

Nadia creates the following assignment. The example is intentionally complete enough to guide a first production pass.

| Field | Pilot assignment |
|---|---|
| Assignment | WORKFORCE-PILOT-001, first teaching draft |
| Person served | A small studio operator or educator learning to coordinate AI-assisted publishing |
| Reader outcome | Prepare a bounded brief and identify an adaptation affected by a source change |
| Requested artifacts | One chapter, one narration script, one short-video script, and one video-book storyboard |
| Input scope | Original fictional examples and the named local draft files |
| Format scope | UTF-8 text; no recording, video rendering, account changes, or commerce |
| Definition of done for this pass | Four source files are present, their declared hashes match, their dependency graph is consistent, and unresolved reviews remain visible |
| Editorial standard | Plain language, a worked case, an exercise, a failure example, and clear limits on claims |
| Human decision | A designated editor must later judge whether the material is useful enough for a reader trial |
| Recovery | Preserve the failed packet, correct the working source, inspect affected adaptations, and build a new packet |

The assignment is not an instruction to perform every possible downstream action. An audio script is a useful result before a narrator is selected. A storyboard is useful before visual assets are commissioned. A publishing brief can be useful before a destination account is connected.

There is also a difference between a role and an account. "Narration editor" identifies work. A label such as ChatGPT Business, Gemini AI, or Claude identifies an intended workspace. It does not establish a connection, a model response, or a completed handoff. The coordinator should preserve both fields without treating either as proof of execution.

The team keeps optional creative ideas in a separate proposal list. A suggestion for animated characters may improve the final video. It does not silently replace the text-only pilot or create a new cost commitment. Nadia can review that proposal after the first result makes the current tradeoff visible.

### 4. Give each role a distinct question

The pilot uses three proposed AI-workspace assignments and a human decision role. These are a coordination design. The accompanying local tools prepare handoff briefs; they do not send them or make the workspaces communicate.

The coordinator asks: "Does this packet preserve the objective, exact source identities, current blockers, and next action?" Its job is to keep the assignment coherent. It should not resolve a disagreement by deleting the objection or marking an unreviewed asset approved.

The adaptation producer asks: "How should the same lesson change for a listener or viewer?" Its job is to make an intentional adaptation. A spoken explanation may need a pause instead of a table. A short video may teach only one decision. The producer records what was shortened and what a viewer must read elsewhere.

The challenger asks: "What could lead a reader to believe something the evidence does not establish?" Its job is to examine the candidate against the assignment and original sources. It should check whether an attractive headline turns a proposal into a promise or whether a compressed narration removes a necessary qualification.

The human editor asks: "Is this specific version suitable for the next intended audience and use?" The answer requires a concrete artifact and a defined decision. An editor accepting a chapter for a small reader trial has not necessarily accepted every adaptation or a public commercial release.

Distinct questions make collaboration easier to evaluate. If every role receives only "improve this," all three may polish the same wording while leaving the same factual gap. The coordinator can instead preserve independent findings and show where they agree, differ, or require a new source.

### 5. Make acceptance criteria specific enough to fail

Useful acceptance criteria allow a reasonable reviewer to reject the work. A criterion such as "high quality" gives too little guidance. A criterion such as "the narration describes the table in words and preserves the distinction between a draft and a released product" gives the reviewer something to examine.

The pilot's source criteria are mechanical. Every declared local asset must be a permitted text file inside the brief's source directory. Its bytes must match the recorded source hash for that revision. Its parent references must identify known assets without a dependency cycle. A derived script must record the exact parent version it used.

The editorial criteria require judgment. The fictional case must remain visibly fictional. The exercise must be possible using the supplied material. Financial examples must identify assumptions. The short video must not promise that an unconnected platform is operational. These questions are appropriate for editorial review, and a file verifier cannot answer them by counting headings.

The learner criteria require observation. Ask a reader to inspect an unfamiliar changed-source example. Can the reader explain the blocker and propose a sensible recovery? A reader who can follow a prepared command may still need help explaining why the result matters. Record those as different observations.

The release criteria depend on the intended use. A recorded audiobook needs listening review and a suitable narration arrangement. A video needs review of actual images, sound, captions, and presentation. A website release needs a verified destination and the relevant publishing authority. This text pilot supplies source material for those decisions while keeping those later activities visible as unfinished work.

### 6. Keep the relationship between versions visible

Suppose Leo drafts the chapter and then adapts it into narration. The narration records the chapter's content hash as its parent version. The short-video script records the same chapter hash. The video-book storyboard records both the chapter and the narration it follows.

The resulting dependency map is small enough to understand:

| Asset | Direct source versions it depends on |
|---|---|
| Chapter manuscript | Independently authored pilot source |
| Narration script | The declared chapter bytes |
| Short-video script | The declared chapter bytes |
| Video-book storyboard | The declared chapter and narration bytes |

A hash is useful because it makes a particular byte representation identifiable. It does not establish that the words are true or that the author has permission to use every source. It does not by itself prove who reviewed the file. Those questions require other evidence.

On Tuesday, Nadia changes the chapter's definition of completion. The old narration still contains the earlier explanation. If the team remembers only filenames, both documents may appear current. If the narration retains the chapter hash it used, the coordinator can identify the mismatch.

There are two separate repair steps. First, update the source record to acknowledge the changed chapter bytes. Second, inspect the adaptations and decide whether they still express the revised lesson. Updating the chapter's declared hash does not perform that editorial work. A child adaptation should not automatically receive a new parent hash merely because the coordinator can calculate one.

If the narration changes after review, the storyboard's narration dependency also matters. A useful production system follows the dependency graph in order and carries upstream blockers into downstream work. It should help the team find the affected region rather than force them to restart unrelated assets.

### 7. Work through the failure instead of hiding it

Inez finds a sentence in the chapter that says a verified packet is ready to sell. She asks the team to replace it with a more precise statement: a verified packet has passed its defined local consistency checks; creative review and release decisions remain separate.

Leo corrects the chapter. The narration still says "ready to sell." A fresh build should reveal that the recorded chapter identity and the current bytes differ. After the brief's chapter hash is updated, the narration's old parent reference should still reveal that it was based on another version.

The team now has useful failure evidence. The coordinator identifies the source mismatch. The producer revises the affected sentence. The reviewer compares the new narration with the revised chapter. The next packet contains the updated source identities and retains an honest account of remaining review work.

The recovery is small and inspectable. The team does not need to discard the whole project or pretend the failed version never existed. Keeping the failed packet allows a learner to explain what the check detected and how the repair addressed it.

A different failure requires a different response. If a source file is missing, the team must provide the intended source or revise the asset declaration. If the brief references a parent that does not exist, the assignment graph must be corrected. If a narration file contains only a title, mechanical consistency may pass while editorial usefulness remains poor. The reviewer must be willing to reject a complete-looking packet for the right reason.

### 8. Compare creative options without losing the lesson

Creative variety is most useful when the team can explain its purpose. For this pilot, the chapter offers the full reasoning. The narration uses a conversational sequence with short pauses. The short video focuses on the changed-source problem. The video book combines the longer narration with a sequence of visual decisions and a practice pause.

Those formats do not need identical wording. They do need an accountable relationship to the underlying lesson. The adaptation note should state what was retained, shortened, omitted, or added. If an added example introduces a new claim, identify the evidence it needs.

Nadia proposes two short-video treatments. One begins with a pile of conflicting drafts. The other begins with a learner trying to decide which file was reviewed. Both could work. The team can compare whether a small reader or viewer trial recognizes the changed-source problem, rather than choosing solely on the number of visual effects.

Accessibility belongs in this comparison. A viewer should be able to understand the decision without relying only on color. A listener should hear the meaning of important on-screen text. Captions must be checked against the recording that actually exists. A storyboard can plan these features, but its existence does not prove the eventual media is accessible.

The team also considers maintenance. A dramatic claim may attract attention but become difficult to support. A concrete teaching example can remain useful when a platform changes because it focuses on a decision the person can understand. The pilot should still check implementation-specific instructions whenever the underlying code or tools change.

### 9. Make production economics inspectable

The studio needs to understand the effort involved in turning a draft into a product. For this lesson, consider an entirely hypothetical future edited digital edition priced at nine dollars. The public repository teaching fixture is not a paid offer, and the following values are not observed costs or market demand.

Assume sixty dollars of fixed cash cost, four production hours valued at twenty dollars per hour, fifty cents of per-unit delivery cash cost, and a variable fee assumption of five percent of price. The fee is forty-five cents per unit. Cash contribution before fixed cost is nine dollars minus ninety-five cents, or eight dollars and five cents per unit.

Eight units would cover the assumed sixty-dollar fixed cash cost. Eighteen units would cover the fixed cash cost plus the eighty-dollar labor opportunity cost. The second calculation values the producer's time; it does not assert that eighty dollars was paid to someone.

At a hypothetical twenty-five units, revenue would be two hundred twenty-five dollars. Variable cash cost would be twenty-three dollars and seventy-five cents. After the sixty-dollar fixed cost, the cash result would be one hundred forty-one dollars and twenty-five cents. After the assumed value of production labor, it would be sixty-one dollars and twenty-five cents.

These figures exclude taxes, refunds, acquisition costs, a separately charged fixed payment fee, ongoing support labor, and any other cost not entered in the model. They do not establish that anyone will buy. The useful question is which assumptions most need evidence before more effort or money is committed.

The team can test the educational usefulness of the pilot before selecting a commercial price. If readers cannot complete the exercise, more advertising is unlikely to fix the lesson. If support time is substantial, the cost model should include it before the team interprets a cash result as a sustainable return.

### 10. A guided workshop

Use a disposable working directory and the public example supplied with this project. Keep the original fixture intact so that you can compare your experiment with a known starting point. You do not need a model key or a connected publishing account for this exercise.

1. Read the objective and audience in the supplied production brief. Restate the reader outcome in your own words.
2. Name the four source assets and explain the role of each format.
3. Draw the direct parent relationships. Identify which asset depends on two parents.
4. Run the local production-plan command into a new directory. Keep its manifest hash with your exercise notes.
5. Run the verifier against that packet. Record both the integrity result and the production/release qualifications.
6. Explain why passing verification does not establish that an audiobook or video has been rendered.
7. In your working copy, change one sentence in the chapter without updating the brief. Build a separate packet and inspect the source mismatch.
8. Update only the chapter's declared hash. Build again and inspect the remaining dependent-asset blockers.
9. Review the affected scripts. Explain which text actually needs to change and why. Do not update parent hashes before that review.
10. After making a justified adaptation, update the relevant source and parent references. Build a new packet and compare the dependency states.
11. Evaluate the supplied economics scenarios. Identify one excluded cost and explain how including it could change the result.
12. Write a short acceptance note naming the exact packet, what you checked, what remains untested, and the next appropriate human decision.

Your submission should include the baseline and changed-source results, the corrected dependency explanation, and the acceptance note. It should not contain real customer information, credentials, or a statement that a fictional teaching result occurred in a real business.

### 11. Assess the work and decide the next step

Use the following rubric as a proposed teaching aid. It has not been validated as a formal assessment instrument.

| Criterion | Evidence to inspect | Successful demonstration |
|---|---|---|
| Assignment clarity | The reader's restated brief | Names the person, output, outcome, scope, and definition of done |
| Source identity | Baseline and changed-source results | Explains the exact mismatch rather than merely reporting an error |
| Dependency reasoning | Graph and recovery explanation | Identifies directly and indirectly affected adaptations |
| Scope awareness | Acceptance note | Separates local source consistency from editorial, media, and release decisions |
| Economic reasoning | Scenario interpretation | Identifies assumptions, time value, excluded cost, and absent demand evidence |
| Human understanding | A new example discussed without the answer key | Applies the same reasoning to an unfamiliar small production task |

If a learner cannot explain a blocker, return to the smallest example that demonstrates it. If the tool output is confusing, record the confusing field and propose a clearer explanation. If the lesson is accurate but too long for the audience, test a shorter treatment while preserving the same acceptance questions.

The next production decision should follow the evidence. A successful local exercise can support an editorial review. A useful editorial review can support a reader trial. A reader trial can inform revision and a later release decision. Each step should make the next judgment easier for a person to understand.
