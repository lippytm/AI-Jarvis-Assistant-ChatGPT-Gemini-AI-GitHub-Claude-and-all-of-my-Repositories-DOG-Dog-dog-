# AI Jarvis Creative Creation Studio v0.1

Owner and final authority: **Charles Earl Lipshay**

## Purpose

Create, compare, test, package, and improve isolated AI Jarvis Assistant prototypes for personal and future customer use. A “clone” is a versioned configuration and capability bundle—not an independent identity, secret copy, or uncontrolled self-replicating system.

## Studio pipeline

1. **Idea intake** — capture the user, problem, outcome, limits, budget, and evidence.
2. **Blueprint** — select roles, skills, providers, tools, memory policy, permissions, and evaluation targets.
3. **Prototype** — generate an isolated, nonproduction Jarvis instance.
4. **Simulation** — run synthetic tasks and adversarial cases without customer or production data.
5. **Diagnostics** — measure correctness, safety, latency, cost, provenance, rollback, and approval compliance.
6. **Comparison** — benchmark the candidate against the current approved baseline.
7. **Review** — produce a change report, risk report, and recommendation.
8. **Promotion** — only Charles may approve promotion, publication, deployment, or customer release.
9. **Feedback** — record verified lessons in approved project memory.

## Initial studio roles

- Studio Director — prioritizes prototype experiments.
- Blueprint Architect — assembles versioned configurations.
- Coding Engine — implements adapters, tools, tests, and interfaces.
- Diagnostic Engine — reproduces failures and verifies repairs.
- Red-Team Reviewer — tests misuse, prompt injection, data leakage, and unsafe authority.
- Evaluation Lab — runs repeatable benchmarks.
- Packaging Agent — creates documentation, examples, and release candidates.
- Provenance Keeper — records inputs, versions, hashes, tests, approvals, and rollback.

## Safety boundaries

The studio must not:

- copy proprietary model weights, private prompts, or third-party code without permission;
- impersonate Charles or other people;
- share credentials, private repository metadata, customer data, or personal records between prototypes;
- let a prototype approve itself;
- modify its own production permissions;
- merge, deploy, publish, spend, send external messages, or perform destructive actions without explicit approval;
- describe a candidate as “super,” “self-healing,” secure, or production-ready without defined evidence.

## First deliverable

Build one **Jarvis Repository Doctor** prototype that analyzes a low-risk repository in read-only mode and returns:

- purpose and technology summary;
- build/test/lint/security commands found;
- documentation gaps;
- reproducible health findings;
- prioritized improvement proposals;
- evidence and uncertainty;
- a rollback-safe implementation plan.

No code changes occur in the first evaluation.
